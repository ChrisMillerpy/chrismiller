RFC

Problem

Cathy works, but the chat screen is bare next to the Claude Code app. Chats can't be named or found. You can't choose the model or how hard it thinks, and you can't stop it mid-task. You can't hand it a file. Anything it makes stays as text in a chat or a commit, with no simple way to view or share it.

Goals

  1. Manage chats: Cathy names them, you rename (your name wins), search, archive and unarchive.
  2. Control the agent: model and effort per chat; stop; interrupt with a new message.
  3. Give her things: attach images and files.
  4. Get things back: artifacts (documents, worksheets, pages, images, PDFs) shown in the chat.
  5. Share them: private (admin only) or anyone with the link.

Not goals: email invites, a public gallery, a cathy CLI, PR or diff views. All are possible later on the same backend.

  • Data. D1 holds the facts: chats (now with named_by, model, effort), uploads, artifacts and artifact_versions. R2 holds the bytes at uploads/<id> and artifacts/<id>/v<n>. Republishing adds a version, and the link always serves the latest.
  • Publishing. Cathy calls publish_artifact(path, title, visibility?, id?). The Worker reads the file from her box, stores it and posts a card in the chat. She never holds storage credentials.
  • Attachments. The page uploads each file first, then sends the message with their ids. The Session keeps only ids that belong to this chat, writes the files into her box at /uploads/, and passes images and PDFs to Claude inline.
  • Model and effort. The choices live in MODELS in cathy/worker/wrangler.jsonc, which is the one source of truth. They're read at the start of every turn and sent to Anthropic as effort plus adaptive, summarised thinking.
  • Stop and interrupt. Each turn has an AbortController. On a stop, her memory keeps only completed steps, so it never holds a tool call without its result. Her thinking isn't stored in memory, because it's signed per model and would break the chat after a model switch.
  • Sharing. A small public Worker, share/, matches only GET|HEAD /a/<20-char token>[/download] and forwards a bare request with no cookies or query string. Cathy answers only for link artifacts. Responses are cached for 60 seconds, so un-sharing takes effect within a minute.

Alternatives considered

OptionWhy not (for now)
A cathy CLI in her box (cathy file publish x.html)It needs a public write endpoint and a token in her box. A tool gives the same result with no new door to the internet. It can still be added later as a layer over the same API.
File bytes in D1 (the first draft on this branch)D1 caps a value at 2 MB and the database at about 500 MB, so files had to be split into pieces. R2 is built for files and has 10 GB free.
R2 keys in Cathy's boxKeys would open the whole bucket. Nothing would be recorded in D1, so no cards and no Artifacts page.
One Access-protected artifacts site with a public path exemptedIt works, but one misconfigured Access rule exposes everything. A separate Worker that can only do one thing is easier to reason about.
Public gallery and email invitesDropped at your request. "Anyone with the link" covers sharing a worksheet.

Security model

  • Admin, the API and private artifacts sit behind Cloudflare Access as before. The share Worker is the only new public surface. It holds no data and no secrets, and forwards a single route.
  • Link tokens are 20 characters from a 32-letter alphabet (100 bits), checked by format before any lookup. "New link" replaces the token.
  • Every stored file is served with Content-Security-Policy: sandbox allow-scripts … and no allow-same-origin, plus nosniff. In admin, previews are also in sandboxed iframes. So an HTML artifact can run its own scripts but can't read your cookies, use storage, or call admin's API. The probe below shows this.
  • Attachment ids are trusted only if they belong to the chat. File names are cleaned. A 25 MB limit is enforced on the server.
  • Cathy's artifacts skill makes artifacts private by default and forbids student or parent details in anything shared.
